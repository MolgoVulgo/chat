# V2 — Évolution moteur de patterns et stockage

## Objectif

Mettre en place une architecture simple et robuste pour gérer des patterns de mouvement évolutifs sans alourdir le firmware.

Principes retenus :

- 5 patterns embarqués en dur dans le firmware ;
- stockage des patterns utilisateur dans LittleFS ;
- outil Python comme source d’édition, validation et export ;
- JSON conservé uniquement côté outil Python ;
- firmware sans parseur JSON ;
- fichier condensé utilisé côté ESP8266 ;
- fallback embarqué obligatoire si LittleFS est vide, absent ou invalide.

---

## Architecture cible

```text
Firmware ESP8266
├─ moteur servo
├─ moteur de session
├─ moteur de patterns
├─ 5 patterns embarqués
├─ loader LittleFS
├─ lecteur format condensé
└─ fallback automatique

LittleFS
├─ /patterns.dat
├─ /patterns.bak
└─ /config.dat ou /config.json

Outil Python
├─ édition des patterns
├─ sauvegarde JSON
├─ validation comportementale
├─ export condensé
└─ génération éventuelle des patterns C embarqués
```

Le firmware exécute. L’outil Python conçoit, valide et exporte.

---

## Séparation des responsabilités

| Bloc | Responsabilité |
|---|---|
| Firmware | exécution temps réel, servos, laser, session, chargement LittleFS |
| Patterns embarqués | base minimale toujours disponible |
| LittleFS | stockage des patterns utilisateur |
| Outil Python | édition, validation, conversion, export |
| JSON | format source lisible côté outil |
| DAT/BIN | format runtime compact côté ESP8266 |

## Modèle de coordonnées

Les patterns doivent être définis dans un espace logique normalisé, indépendant de la pièce et des angles servo.

```text
x = 0..1000
y = 0..1000
```

Le moteur ne travaille pas directement en degrés servo.

Conversion :

```text
coordonnées logiques
→ workspace actif
→ calibration pan/tilt
→ consignes servo
```

Avantages :

- patterns réutilisables quelle que soit la zone de jeu ;
- calibration indépendante ;
- pas besoin de régénérer les patterns après changement de montage ;
- précision supérieure à un simple 0..100 sans utiliser de float.

## Configuration workspace

La configuration runtime doit contenir les paramètres nécessaires à l’adaptation physique.

Champs recommandés :

```text
pan_min
pan_max
pan_center
pan_invert

tilt_min
tilt_max
tilt_center
tilt_invert

workspace_x_min
workspace_x_max
workspace_y_min
workspace_y_max

speed_scale

```

Les dimensions physiques peuvent être optionnelles :

```text
surface_width_cm
surface_height_cm
surface_distance_cm
```

Ces valeurs servent à estimer ou documenter la zone, pas à rendre le moteur dépendant d’une géométrie réelle stricte.

## Patterns embarqués

Le firmware contient 5 patterns de base.

Objectifs :

- garantir un fonctionnement même sans LittleFS ;
- permettre un démarrage sûr ;
- éviter une dépendance critique au stockage externe ;
- disposer d’un comportement minimal après reset ou corruption des fichiers.

Patterns recommandés :

```text
idle_wander
slow_hunt
short_escape
loop_play
calm_end
```

Chaque pattern embarqué doit utiliser le même format interne que les patterns chargés depuis LittleFS, afin d’éviter deux moteurs différents.

---

## Patterns utilisateur

Les patterns utilisateur sont stockés dans LittleFS sous forme condensée.

Fichier principal :

```text
/patterns.dat
```

Fichier de secours :

```text
/patterns.bak
```

Fichier temporaire lors d’un upload :

```text
/patterns.tmp
```

Workflow d’écriture :

```text
1. écrire /patterns.tmp
2. vérifier taille + checksum
3. renommer /patterns.dat vers /patterns.bak
4. renommer /patterns.tmp vers /patterns.dat
5. recharger les patterns
```

En cas d’échec :

```text
- conserver les patterns actifs en RAM ;
- ignorer le fichier invalide ;
- revenir aux patterns embarqués si nécessaire.
```

---

## Format condensé

Le format runtime doit être binaire, simple, versionné et validable sans allocation complexe.

Nom recommandé :

```text
patterns.dat
```

Structure logique :

```text
Header
├─ magic
├─ version
├─ header_size
├─ file_size
├─ pattern_count
├─ flags
└─ checksum

Pattern[]
├─ id
├─ weight
├─ mode
├─ point_count
├─ duration_total_ms
└─ points[]

Point[]
├─ x
├─ y
├─ duration_ms
├─ laser
├─ easing
└─ flags
```

---

## Header proposé

Champs recommandés :

```text
magic               4 bytes   "LPTN"
version             uint16
header_size         uint16
file_size           uint32
pattern_count       uint16
reserved            uint16
checksum_crc32      uint32
```

Version initiale :

```text
PATTERN_FORMAT_VERSION = 1
```

Le firmware doit refuser tout fichier dont :

- le magic est invalide ;
- la version est inconnue ;
- la taille annoncée ne correspond pas ;
- le nombre de patterns dépasse la limite ;
- le checksum échoue.

---

## Structure pattern proposée

```text
id                  char[24]
weight              uint8
mode                uint8
point_count         uint16
duration_total_ms   uint32
flags               uint16
reserved            uint16
```

Règles :

- `id` unique ;
- ASCII simple ;
- pas d’espace ;
- longueur maximale contrôlée côté Python ;
- `weight` entre 1 et 255 ;
- `point_count` borné.

---

## Structure point proposée

```text
x                   uint16   // 0..1000
y                   uint16   // 0..1000
duration_ms         uint16
laser               uint8    // 0/1
easing              uint8
flags               uint16
```

Taille indicative : 10 bytes par point.

Exemple de coût :

```text
20 patterns × 64 points × 10 bytes = 12 800 bytes
```

Même avec les headers, le fichier reste très petit.

---

## Easing

Enums recommandés :

```text
0 = linear
1 = smoothstep
2 = ease_in
3 = ease_out
4 = ease_in_out
5 = hold
```

Par défaut :

```text
smoothstep
```

Le firmware doit accepter uniquement les valeurs connues. Toute valeur inconnue doit être remplacée par `smoothstep` ou provoquer le rejet du pattern selon le niveau de strictesse retenu.

---

## Limites runtime

Valeurs recommandées :

```text
MAX_BUILTIN_PATTERNS      5
MAX_USER_PATTERNS         20
MAX_TOTAL_PATTERNS        25
MAX_POINTS_PER_PATTERN    64
MAX_PATTERN_FILE_SIZE     65536
MIN_POINT_DURATION_MS     80
MAX_POINT_DURATION_MS     5000
MAX_PATTERN_DURATION_MS   180000
```

Objectif : éviter les allocations dynamiques et préserver une empreinte RAM prévisible.

---

## Chargement des patterns

Séquence au boot :

```text
1. initialiser le pool de patterns
2. charger les 5 patterns embarqués
3. monter LittleFS
4. chercher /patterns.dat
5. valider le fichier
6. charger les patterns utilisateur valides
7. construire le pool actif
8. démarrer en état idle
```

Si LittleFS échoue :

```text
- log erreur
- garder uniquement les patterns embarqués
- continuer le boot
```

Si `/patterns.dat` est invalide :

```text
- tenter /patterns.bak
- si bak valide : l’utiliser
- sinon : fallback embarqué
```

---

## Remplacement des patterns

Règle recommandée :

```text
si ID utilisateur == ID embarqué → remplacement
si ID utilisateur inconnu → ajout
```

Avantages :

- les patterns de base peuvent être ajustés sans reflasher ;
- les patterns embarqués restent disponibles après reset LittleFS ;
- le comportement reste simple à comprendre.

Une fonction de reset doit supprimer :

```text
/patterns.dat
/patterns.bak
/patterns.tmp
```

Puis recharger les 5 patterns embarqués.

---

## Moteur de rendu

Le moteur de rendu doit rester simple.

Responsabilités :

```text
- lire le point courant ;
- interpoler vers le point suivant ;
- appliquer easing ;
- convertir x/y logique vers pan/tilt ;
- envoyer les consignes servo ;
- gérer laser ON/OFF ;
- respecter les durées.
```

Il ne doit pas :

```text
- parser JSON ;
- générer des formes complexes ;
- connaître la géométrie réelle de la pièce ;
- dépendre de LittleFS pour fonctionner.
```

---

## Génération de formes côté outil Python

Les formes et comportements doivent être générés côté outil Python, puis exportés sous forme de points.

Primitives côté outil :

```text
line
arc
loop
spiral_in
spiral_out
zigzag
jitter
pause
escape
calm_return
```

Le firmware ne voit pas ces primitives. Il reçoit uniquement des points déjà résolus.

Pipeline :

```text
primitive logique
→ sampling en points
→ validation
→ export JSON source
→ export patterns.dat
```

## JSON source côté outil

Le JSON reste le format lisible et éditable.

Rôle :

```text
- sauvegarde de projet ;
- édition manuelle possible ;
- versionnement Git ;
- génération du fichier condensé ;
- génération éventuelle des patterns embarqués C.
```

Le JSON ne doit pas être chargé par le firmware.

Structure logique :

```text
metadata
├─ format_version
├─ name
├─ author
└─ description

workspace
├─ width
├─ height
└─ units

patterns[]
├─ id
├─ weight
├─ tags
├─ steps/primitives
└─ resolved_points
```

L’outil peut stocker à la fois :

- les primitives sources ;
- les points résolus ;
- les métadonnées de validation.

## Export condensé côté Python

L’outil Python doit produire :

```text
patterns.dat
```

Et optionnellement :

```text
patterns_report.txt
patterns_preview.png
builtin_patterns.c
```

Étapes d’export :

```text
1. charger JSON
2. résoudre les primitives en points
3. normaliser x/y en 0..1000
4. valider les contraintes
5. construire le binaire
6. calculer checksum
7. écrire patterns.dat
8. produire un rapport de validation
```

---

## Validation côté Python

Le Python doit effectuer la validation forte.

Contrôles obligatoires :

```text
- ID unique ;
- nombre de patterns ;
- nombre de points par pattern ;
- coordonnées dans 0..1000 ;
- durée min/max par point ;
- durée totale par pattern ;
- vitesse maximale entre deux points ;
- accélération excessive ;
- ratio laser ON/OFF ;
- absence de sauts absurdes laser ON ;
- poids valide ;
- easing connu ;
- taille finale du fichier.
```

Le rapport doit indiquer :

```text
OK
WARN
ERROR
```

Un export contenant des erreurs bloquantes doit être refusé.

---

## Validation côté firmware

Le firmware doit faire une validation défensive, pas comportementale.

Contrôles nécessaires :

```text
- magic ;
- version ;
- taille ;
- checksum ;
- pattern_count ;
- point_count ;
- bornes x/y ;
- bornes duration ;
- valeurs easing ;
- taille lue cohérente.
```

Si validation échoue :

```text
- ignorer le fichier ;
- conserver le pool actuel si déjà chargé ;
- sinon fallback embarqué.
```

---

## Gestion mémoire

Éviter les allocations dynamiques.

Modèle recommandé :

```text
pattern_pool[MAX_TOTAL_PATTERNS]
point_pool[MAX_TOTAL_POINTS]
```

Ou variante :

```text
patterns fixes
points fixes par pattern
```

À éviter :

```text
malloc par pattern
malloc par point
fragmentation heap
parsing texte runtime
```

Le fichier condensé peut être lu en streaming, mais une première version peut charger un buffer limité si la taille max reste faible.

## LittleFS

Usage LittleFS :

```text
- stocker patterns.dat ;
- stocker backup ;
- stocker config ;
- permettre reset sans reflasher.
```

Règles :

```text
- aucun fichier LittleFS ne doit être indispensable au boot ;
- tout fichier invalide doit être ignoré proprement ;
- upload par fichier temporaire ;
- backup avant remplacement ;
- reset possible.
```

---

## Configuration runtime

Deux options possibles :

### Option A — config JSON

Avantage : lisible.

Inconvénient : nécessite un parseur ou parser minimal.

### Option B — config condensée

Avantage : cohérente avec les patterns, lecture simple.

Inconvénient : moins éditable directement.

Choix recommandé :

```text
config simple en texte clé=valeur ou JSON minimal si déjà présent
patterns en binaire condensé
```

Le besoin critique est surtout d’éviter le JSON pour les patterns, pas forcément pour 10 paramètres de configuration.

---

## Upload et reload

Le système doit permettre :

```text
- upload de patterns.dat ;
- vérification du fichier ;
- activation après validation ;
- rollback si échec ;
- reset vers patterns embarqués.
```

Comportements attendus :

```text
upload OK → patterns actifs remplacés
upload KO → patterns actifs conservés
reset → suppression LittleFS patterns + fallback embarqué
reboot → chargement automatique du meilleur fichier valide
```

---

idle

```text
- pas de reload patterns pendant exécution ;
- arrêt propre avant remplacement du pool actif ;
- fallback immédiat si chargement invalide ;
- laser OFF pendant chargement ou reset patterns.
```
